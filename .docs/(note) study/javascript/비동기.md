### XMLHttpRequest  
생성자 함수를 호출하여 생성 WebAPI라 브라우저에서만 정상실행

const xhr = new XMLHttpRequest();

xhr 객체의 메서드
- open 초기화  
- send 전송  
- setRequestHeader 헤더 설정

xhr.open(method, url)  
method는 get post put delete등을 쓰는 자리고  
url은 말 그대로 컨트롤러에서 받아줄 요청주소  

http의 요청 메서드는 주로 5가지 사용
- get 모든/특정 리소스의 취득
- post 리소스 생성
- put 리소스의 전체 교체
- patch 리소스의 일부 수정
- delete 모든/특정 리소스의 삭제

뭐 이런게 있었는데 이건 이제 구형이라 fetch를 씀  
프로미스라는 개념을 이해하면 얘가 더 간결하고 직관적으로 사용할 수 있으며,  
굳이 사용자가 수동으로 처리하지 않더라도 자동으로 json 형태로 변환해오니깐.

## 프로미스

대충 위만 이용해서 한 처리는 코드를 제대로 안 짜면  
비동기 함수가 끝나기도 전에 기존 함수가 종료해버려서  
제대로 작동하지 않을 가능성도 있으며  
그것을 해결하기 위해 콜백함수를 막 쌓기 때문에  
보기도 처리하기도 어려워지는 상황이 발생했음.  

그래서 등장한 것이 프로미스. 

생성자를 통해 생성하고 resolve와 reject를 인수로 받는데, 비동기 처리 성공시 resolve 함수를 호출
실패시 reject 함수를 호출함.

### 프로미스의 상태
- 처리 중 pending  
- 처리 완료 settled
    - 성공 fulfilled
    - 실패 rejected

### 처리 완료 후 후속 처리 메서드
- then
- catch
- finally

어떻게 쓰냐  
then은 두 개의 콜백 함수를 인수로 받지만 catch랑 같이 쓰기 때문에 하나만 써도 됨  
.then(함수);  
.catch(함수);  

두개의 콜백 함수를 인수로 받는다는 건 fulilled 상태가 됐을 때와 rejected 상태가 됐을 때 각각 실행함 함수를 받을 수 있다는 말임.  

.then(fulfilled시 실행될 함수,rejected시 실행될 함수.);  
promise의 결과에 따라서 앞에 함수는 무조건 fulfilled 시에만, 뒤에건 rejected 시에만 실행되도록 되어있음.  
null을 넣을 수도 있음.  

프로미스 체이닝을 할 때에는
값이 return 되면 다음 fulfilled 상태인 거고, throw를 하면 rejected 상태인 것임.

### 결론
promise를 써서 어느정도 xhr의 처리를 보기 좋고 용이하게 할 수 있는데,  
이마저도 가독성이 나쁘기 때문에 async/await을 사용하게 됨.  
async/await을 쓰면 후속 처리 메서드 없이 구현할 수 있기 때문.

### promise의 정적 메서드
- .resolve() 인수로 전달받은 값을 resolve하는 프로미스
- .reject() 인수로 전달받은 값을 reject 하는 프로미스
- .all() 여러 개의 비동기 처리를 병렬로 처리할 때 사용함. 하나라도 reject 상태가 되면 나머지가 fulfilled 상태가 되는 것을 기다리지 않고 즉시 종료.
- .race() 가장 먼저 fulfilled 상태가 된 프로미스의 처리결과를 resolve하는 새로운 프로미스 반환
